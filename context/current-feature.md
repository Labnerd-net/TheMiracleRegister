### Patronage Browse Pages (backlog #51)
`saints.patronage` is free text (69 distinct terms across published saints, 59 on one saint, near-duplicates such as families / Catholic families / parents, plus places and organizations), so it could not be browsed like topics and themes. Added `PATRONAGE_GROUPS` in `src/db/topics.ts` (10 groups: families, the-sick, youth, world-youth-day, converts, education, native-peoples, missions, environment, pro-life; slug, label, aliases). `src/lib/patronage.ts` resolves each raw string to a group, or to its own term with a slugified name; matching ignores case and whitespace. A term gets a page at `MIN_PATRONAGE_SAINTS = 2` published saints, and related saints (pairs) count toward it by decision, so every existing page is indexable. New `/patronage` lists all terms alphabetically: terms with a page link to `/patronage/[term]`, single-saint terms link straight to the saint. `/patronage/[term]` redirects an unknown slug to `/404` and a term that fell to one saint to that saint. Saint page patronage tags keep their original text and link to the term page when one exists; the sitemap lists `/patronage` and qualifying terms; the footer links to Patronage. `check:data` flags a group alias with wrong case or spacing, blank strings, a singleton whose slug collides with a group slug, and two strings sharing a slug; it deliberately does not flag ungrouped singletons. Data edit in production: "The sick" and "sick people" normalized to "the sick" on Andre Bessette and Bernadette Soubirous. Live term pages at merge: converts, education, families, Fatima, native-peoples, pro-life, sick-children, the-sick, world-youth-day, youth. Verified: typecheck, build and 160 tests (13 new, `tests/patronage.test.ts`) pass; `check:data` clean; on the dev server against production data, the index and group pages returned 200, a singleton and a collapsed term redirected to the saint, an unknown slug to `/404`, and the sitemap listed the term pages; CI `check` and the Workers Builds branch build passed on PR #16. Not verified: browser rendering, the production deploy of `main` (`e1a02b4`), search-engine indexing, and mutation checks on the new tests. Trade-offs: Fatima and sick-children (Marto siblings) and part of families (Martin spouses) have pages only because related saints count; places and organizations (France, Lourdes, Opus Dei) appear on the index as singleton terms, since there is no field marking them; saint pages with patronage now load patronage for all published saints (about 26 rows) to decide which tags to link; "sick children" was kept separate from "the sick" and "mothers" from families. Follow-up (PR #17): the index showed mixed capitalization, so patronage is now sentence case (first letter capitalized, then lowercase except proper nouns and acronyms). Production edit: first letter capitalized on every patronage string (24 saints; "The sick" is now capitalized again; 69 distinct terms became 67 where two differed only by case). `check:data` errors on a patronage string with a lowercase first letter, `PATRONAGE_GROUPS` aliases use the capitalized spellings, ungrouped terms are capitalized at render as a fallback, and `CLAUDE.md` documents the rule. Not enforceable by script: capitals in the middle of a string (e.g. "Catholic Families" would pass). Verified: typecheck, build, 160 tests and a clean `check:data`; CI `check` and the Workers Builds branch build passed on PR #17. Not verified: the live index in a browser or the production deploy of `main` (`110d3be`).

### Rate Limiter on Workers Rate Limiting Binding (backlog #16)
The KV rate limiter did a KV read plus write on the same key for every API request and search; KV allows about 1 write/s per key and bills writes, the read-then-write was non-atomic, and any KV error was uncaught, so a KV hiccup became a public 500 on the whole API and `/search`. Replaced the `RATE_LIMIT` KV binding with two Workers Rate Limiting bindings in `wrangler.jsonc`: `API_RATE_LIMITER` (60 per 60s, namespace_id `16001`) and `SEARCH_RATE_LIMITER` (30 per 60s, namespace_id `16002`). `isRateLimited(limiter, key)` in `src/lib/rateLimit.ts` is now one `limit()` call and fails open: if the limiter throws it logs and allows the request. The limits now live in `wrangler.jsonc` instead of code constants. Tests use a fake limiter (`tests/helpers/apiApp.ts`, `tests/rate-limit.test.ts`, with a new fail-open test). Verified: typecheck, build and 146 tests pass; on the dev server the API served exactly 60 requests then returned 429 with the error envelope, and `/search` served exactly 30 then 429; the built `wrangler.json` carries both `ratelimits` entries; CI `check` and the Workers Builds branch build passed on PR #14, and the production Workers Builds deploy of `main` (`07dd2b3`) succeeded. Not verified: behaviour on the deployed edge (a curl loop against `https://themiracleregister.org/api/v1/types` got `403 Your request was blocked.` on every request, which is not this app's response, so a Cloudflare rule in front of the site blocks that client and the limiter was never reached; fail-open also means a broken binding would not show as an error), and that `namespace_id` 16001/16002 are unused by other Workers on the Cloudflare account (a collision would share counters). Trade-offs: counters are per Cloudflare location and eventually consistent (Cloudflare documents the binding as permissive, not an accounting system), so a client spread across locations can exceed the nominal limit; KV was also eventually consistent, so this is a loosening rather than a new weakness. A limiter outage now allows traffic instead of returning 500. Left over: the old KV namespace (`d7ad4bf2b80f497e95b58860f8c0384f`) is unbound and can be deleted by hand; the `SESSION` KV binding in the build output is added by the Astro Cloudflare adapter and was not touched.

### Foreign-Key Indexes (backlog #17)
Child-table lookups had no index on the column pages join or filter by, and `miracle_saints` had only the `(miracle_id, saint_id)` PK, which cannot serve `WHERE saint_id = ?`. Migration 0033 adds `miracle_saints (saint_id)`, `miracle_sources (miracle_id)`, `miracle_images (miracle_id, display_order)` (pages fetch images ordered by `display_order`), `saint_sources (saint_id)` and `saint_locations (saint_id)`. Applied to production before the merge (migrations 33 -> 34); all five confirmed in `pg_indexes`, and `check:data` showed only #49. Typecheck, build and 146 tests pass; CI `check` passed on PR #13. No measurable speedup today: the largest table has 219 rows, so Postgres will keep choosing sequential scans; this is future-proofing for lookups the code already makes and for cascade deletes. Deliberately not added, differing from the backlog text: `saint_relations (saint_id)` (the PK already leads with it, and `related_saint_id` is never filtered on), `published` on saints and miracles (boolean, low selectivity), and `miracles.date_of_event` (the year filters use `EXTRACT(YEAR FROM date_of_event)`, which a plain btree cannot serve; it would need an expression index, so revisit if the table grows). Not verified: that the planner uses the new indexes (not observable at these row counts) and the deployed site. #17 is closed; the `published` and `date_of_event` ideas are not carried forward as backlog items.

### Slug Redirects and Snapshot Schedule (backlog #45)
All edits are raw SQL against the single production Neon branch, so a slug rename silently broke the old public URL and nothing recorded the old slug, and the branch had no snapshots (point-in-time history is 6 hours). Added the `slug_redirects` table (`entity_type`, `old_slug`, `new_slug`, unique on type + old slug; migrations 0031 and 0032) and `AFTER UPDATE OF slug` triggers on `saints` and `miracles` that record a redirect on any rename, from the app or raw SQL. Chains stay one hop and renaming back removes the old redirect so it cannot loop. `/saints/[slug]` and `/miracles/[slug]` now return a 301 to the new slug on a miss (`src/lib/slugRedirect.ts`, 60s `Cache-Control`), skipped when a valid preview token is present; unknown slugs still redirect to `/404`. `npm run check:data` flags a redirect whose old slug is live again or whose target does not exist. Set outside the code: Neon snapshot schedule on `br-proud-block-aptdevzb`, daily 08:00 UTC with 14 day retention, plus a manual snapshot `pre-slug-redirects-migration` (`snap-soft-pond-ap6ydc11`, expires 2026-10-31) taken before the migration. Migrations were applied to production before the merge, because the pages query the table on every slug miss. Verified: typecheck, build and tests (146, 6 new, on PGlite) pass; on production, a rename-twice inside a rolled-back transaction gave a one-hop chain and persisted nothing; on the dev server, temporary redirect rows (deleted) gave 301s with the right `Location` and `Cache-Control` for a saint and a miracle, and unknown slugs went to `/404`; `check:data` after migrating showed only #49; CI `check` passed on PR #12. Not verified: a valid preview token against a redirecting slug, mutation checks on the new tests, the Neon HTTP driver in the tests, the deployed site, and restoring from a snapshot. Not done: redirects for slugs renamed before the migration (no history exists), API redirects (`/api/v1/*/:slug` still 404s), keeping `?preview=` across a redirect. Trade-off: a 301 is cached for up to 60s at browsers and the edge, so a rename-back can briefly redirect to the wrong place.

### Cache Behavior (backlog #14, #18)
Pages sent `public, max-age=N` with 24h `stale-while-revalidate`, so browsers and shared caches held content for the full TTL, and Today's Feast could be a day stale after midnight UTC. Data is edited in Neon with no purge hook. Added `src/lib/cache.ts` with three policies: `CACHE_CONTENT` (`max-age=60, s-maxage=900, swr=3600`) for saint/miracle pages, their lists and the saints/miracles API; `CACHE_DAILY` (`max-age=60, s-maxage=300`, no SWR) for the homepage and `/calendar`; `CACHE_REFERENCE` (`max-age=600, s-maxage=3600, swr=3600`) for `/api/v1/types` and `/metadata`. Valid-token previews stay `no-store`, `/random` and `/api/v1/search` unchanged. `tests/api-http.test.ts` now asserts against the constants. Verified: tests (140), typecheck and build pass; headers checked on the dev server for each page group. Not verified: that the Workers edge cache honours `s-maxage` (`wrangler.jsonc` has `cache.enabled`, but I did not check how it behaves in production), so the edge staleness bounds are unconfirmed. Trade-off: more origin and Neon hits, since edge TTLs dropped from 30-60 min to 5-15 min and browsers revalidate after 60s. Not changed: API error responses (404, 400) still get the success cache header from the route middleware; the saint, miracle and `/saints`/`/miracles` list pages still do not purge after an edit, so an edit can take up to about 15 minutes (plus SWR) to appear.

### Fix Today's Feast Off-by-One for Movable Feasts (backlog #11)
